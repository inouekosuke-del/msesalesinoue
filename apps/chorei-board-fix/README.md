# 朝礼ボード データ層の診断・修復ツール

[`docs/chorei-board-audit-2026-09-13.md`](../../docs/chorei-board-audit-2026-09-13.md) で
検出した不具合のうち、**データ側だけで直せるものを直す**ための追加スクリプト。

アプリ本体には触らない。関数名も日本語なので既存の関数と衝突しない。
シートは名前ではなくヘッダー行の組み合わせで特定するので、シート名が変わっても動く。

| ファイル | 役割 |
|---|---|
| `ChoreiFix.gs` | 診断と修復 |
| `ChoreiAgg.gs` | 「正しい集計」の参照実装。画面の数字と突き合わせる対照表を作る |
| `ChoreiPick.gs` | 朝礼の案件候補の絞り込み。受注済み・ロストを候補から外す |
| `ChoreiOrder.gs` | 指示を「施策・件数・対象・期限」で出す。完了したら消えるようにする |
| `test/` | GASをスタブしてNodeで流す回帰テスト |

## 手順

### 1. 追加する

朝礼ボードのスプレッドシート → **拡張機能 > Apps Script**。
`ChoreiFix.gs` と `ChoreiAgg.gs` を新規ファイルとして貼る。

### 0. まず二重取り込みを止める（コード不要・1分）

Apps Script の**トリガー画面で、夕方の取り込みトリガーを 18:00 から 18:10以降にずらす**。

レポートメールは 18:00:05〜18:00:42 に届くのに、取り込みが 18:00:2x に走って
競合している。取りこぼした夕の便は翌朝 07:30 の回が今朝の便と一緒に処理するため、
案件数がちょうど倍になる（9/10〜9/12 に発生）。**放置すると次の平日の翌朝に再発する。**

朝礼の前に `二重取り込みチェック()` を実行すると、
その日の数字が二重の影響を受けていないか判定できる。

### 2. 診断する（読み取りのみ）

`診断()` を実行。`_診断レポート` シートに出る。2026-09-13 のデータでの結果:

| 区分 | 項目 | 件数 |
|---|---|---:|
| 取り込み | 1回で2ファイル以上を処理した日 | **4日**（9/10・9/11・9/12 は案件が約2倍） |
| 取り込み | 中身まで同一の重複行 | 6 |
| 月キー | 日付セルになっている月キー | **9,440**（= 全行×2列） |
| 名寄せ | 案件の `ownerId` が空 | 134行 / **￥119,059,295** |
| 名寄せ | 日次履歴の `memberId` が空 | 213行 |
| キー | `lineId` の衝突（別案件が同一キー） | 172キー |
| キー | `oppId` が空 | 4,720 / 4,720行 |
| 目標 | members と 月別目標 の食い違い | 3件 |
| 目標 | 月別目標に行が無い在籍メンバー | 8名 |
| TODO | `todoTitle` が埋まっている行 | 0 / 2,042 |
| 指示 | 完了済みなのに `active=TRUE` | 10 / 12 |

### 3. 名寄せできない担当を登録する

`メンバー追加候補()` を実行。`メンバー` シートに貼れる行がログに出る。
吉牟田さん・小菅さんは Slack ID まで埋まる。**追加してから修復に進むこと。**

退職・異動済みなら `active` を `FALSE` に。過去分の名寄せは `active` に関係なく効く。
`API Integration` はシステムアカウントなので、名寄せ対象から自動で外れる。

### 4. 修復する

```
修復_ドライラン()   ← 何をどう変えるかだけ出す。書き込みなし
修復_実行()         ← バックアップを作ってから適用する
```

直すのは2種類:

| 直すもの | 規模 | やり方 |
|---|---:|---|
| 月キー列（日付型 → テキスト） | 9,440セル | 列を `setNumberFormat('@')` にしてから `setValues()` で一括 |
| 担当者の名寄せ（`ownerId` / `memberId`） | 481セル | セル単位 |

**月キーはセル単位で直しても直らない。** 文字列を書いてもGoogleスプレッドシートが
また日付に変換するため、先に列をテキスト書式にする必要がある。
そのため書き込みは列ごとの一括（`setValues` 2回）で行う。
9,440セルをセル単位で書くと実行時間を使い切る。

`修復_実行()` は最初に `DriveApp.makeCopy()` でスプレッドシート全体のコピーを作る。
URLは実行ログに出る。行の削除はしない。何度実行しても結果は同じ（冪等）。

### 5. 数字を突き合わせる

`検算_今月()` → `_集計検算` シートに担当者別の受注／計上見込みが出る。
**これと画面の数字が合わなければ、画面側の集計が間違っている。**

`ChoreiAgg.gs` が守っている4つの約束:

1. **`side` を必ず指定する** — 案件は受注行と計上行の2行ある。省くと必ず倍になる
2. **月キーは `toMonthKey_()` を通す** — Dateでも文字列でも同じ結果になる
3. **担当は名寄せしてから集計する** — `ownerId` が空でも `ownerName` から引き直す
4. **知らない進捗は捨てずに返す** — `unknownStages` に出る。SFに進捗が増えても静かに消えない

## 案件候補から受注済みを外す（`ChoreiPick.gs`）

いまの候補は取込_案件をほぼそのまま出していて、**82%が選ぶ必要のない案件**になっている。

| | 件数 | 割合 |
|---|---:|---:|
| 受注済み以上（入金済・検収済・請求書依頼済・請求書発行済・納品済・受注） | 1,157 | 49% |
| ロスト・ペンディング | 775 | 33% |
| **生きている案件** | **428** | **18%** |

`案件候補(memberId)` がこの絞り込みをした配列を返す。確度の高い順→金額の大きい順。
担当を指定すると植松さん33件・広瀬さん61件まで落ちる。

```javascript
案件候補('uematsu')                            // 既定：受注済み・ロスト・期日超過を除く
案件候補('uematsu', { includeDead: true })      // 掘り起こし用にロストも含める
案件候補(null, { overdueOnly: true })           // 期日超過だけ（別枠で出す用）
```

`候補ノイズ診断()` で現状の内訳が出る。

## 上長からの指示を「施策・件数・対象・期限」で出す（`ChoreiOrder.gs`）

いまの `指示` は text（自由記述）と due しか無く、「何件やったか」を数えられない。

新しい仕組みは作らない。同じ軸は `挽回コミット` シートが既に持っているので
（`act` / `count` / `done` / `due` / `refId`）、それに合わせて `指示` を拡張する。
施策名の正は `アクションプラン` シート（`partner`＝パートナー施策 など）。

```
指示_列を追加_ドライラン()   → actionId, targetKind, targetRef, count, doneCount
指示_列を追加_実行()         → 末尾に足すだけ。既存の行と列には触れない
```

既存の指示は空欄のまま残り、従来どおり text だけの指示として動く。

```javascript
指示を出す({
  scope: 'one', targetId: 'uematsu',
  actionId: 'partner',          // アクションプラン シートの id
  targetKind: 'list',
  targetRef: '代理店リスト',      // どこに対して
  count: 5,                     // 何件
  due: '2026-09-20 18:00',      // いつまで
  must: true
});
// → 「パートナー施策 を 代理店リスト に対して 5件、9/20 18:00 まで」
```

`指示を検証()` が出す前に弾く: 施策が存在しない / 件数が0以下 / 期限が過去 /
担当がメンバーに居ない / 対象が空。

`指示の消化状況(memberId)` が「0/5」形式の消化率つき一覧を返す。
期限切れ・必達が上に来る。

### 完了したら消える

完了操作が `doneAt` を書くだけで `active` を落としていないため、
一覧の抽出条件が `active` を見ていると完了しても消えない
（実データで12件中10件が「完了済みなのに active=TRUE」だった）。

```
指示を完了にする(id)              doneAt / doneBy / active=FALSE を同時に書く
                                  行番号ではなく id で探すので、並び替えでずれない
指示_完了済みを片付ける_ドライラン()  いま残っている完了済みを一覧する
指示_完了済みを片付ける_実行()       それらの active を FALSE にする（バックアップ付き）
```

実データで 12件 → 未完了の2件だけになることを確認済み。行は消さないので、
戻したければ `active` を `TRUE` に戻せばよい。

## このツールで直らないもの

| 不具合 | 直す場所 |
|---|---|
| 二重取り込みの恒久対策（全ファイルをマージして1度書く） | GAS本体の取り込み処理。※トリガー時刻をずらす応急処置は上の「手順0」 |
| `oppId` が全行空 / TODOの件名・状況が空 | Salesforceレポートの取得列 |
| 完了した指示が再表示される（本体の抽出条件そのもの） | GAS本体。※データ側の応急処置は `指示_完了済みを片付ける_実行()` |
| クリックで先頭にスクロールする | 本体のHTML/JS |

**`active` を落とす修復は入れていない。** 本体が `active` をどう使っているか
分からないまま落とすと、指示が画面から消える方向に壊れるため。

## 取り込み側を直すとき

`toMonthKey_()` / `safeDate_()` / `normName_()` / `memberIndex_()` /
`isNonMemberOwner_()` は `ChoreiFix.gs` に単独で完結する形で置いてある。
本体の取り込み処理からそのまま呼べる。そうすれば以後は修復が要らなくなる。
