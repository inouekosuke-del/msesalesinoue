# MSE朝礼ボード 集計不具合の調査（2026-09-11）

## 何を調べたか

「個人の受注見込みなどの数字が、うまく集計できていない」という指摘を受け、
朝礼ボードのデータ層 [`MSE朝礼ボード_データ`](https://docs.google.com/spreadsheets/d/18FYRRykL5krlrZe3Sq4hJtl7ZIAUsoX4AxS9RX6QyOU/edit)
（22シート・全行）を読み込んで、実データから検算した。

**GASのソースコードは読めていない。** 朝礼ボードのスクリプトはスプレッドシートの
コンテナバインド型で、Drive APIの検索結果にも出てこない。Drive上のフォルダ
`MSE朝礼ボード_ソース`（`1hVnWNMttCtTdvkplcconwtcENYcgI-MS`）は作成されただけで中身が空。
したがって以下は **データに残った証拠からの診断** であり、コードの該当箇所までは特定できていない。
修正方針は示すが、当てるにはソースが要る（→ [最後のセクション](#次にやること)）。

対象データの取り込み時刻は `2026-09-11 07:30:43`（案件・TODO）。

---

## 結論

数字が合わない原因は1つではなく、**取り込み段階で5つ、集計段階で3つ**の欠陥が重なっている。
金額インパクトの大きい順に並べると、

1. 取り込み元が**計上予定レポート**で、パイプライン確度（A/C/C+）が1件も入っていない。
   生きている見込み案件は6件・403万円しかなく、案件テーブルの金額の66%はロスト・ペンディング
2. 担当者マスタに載っていない人（吉牟田・小菅・重松）の数字が **全部ゼロ扱いで消える**
3. 月キーのゼロ埋め漏れで **22セルが別の月に集計される**

この3つを直さない限り、画面上の個人別受注見込みは何をどう足しても実態と合わない。

## 検出した不具合

### 1. 【致命】読んでいるレポートが違う — 見込み案件がほぼ入っていない

同じSalesforce取り込みで入ってくる2つのシートの間で、案件数が一桁違う。

| シート | 参照している案件数（ユニーク） |
|---|---:|
| 案件（deals） | **63件** |
| TODO | **304件** |

TODOシートが参照している304件のうち **243件は案件テーブルに存在しない**。
その243件の想定金額（`lineId` 末尾の金額を合計）は **約257,055,092円**。
一方、案件テーブルに入っている全案件の受注金額合計は **32,267,800円**。

落ちている案件の担当者内訳（TODO行数ベース）:

| 担当 | 行数 |
|---|---:|
| 伊集院 隼人 | 67 |
| 広瀬 友樹 | 53 |
| 植松 慶行 | 30 |
| 木戸 悠登 | 27 |
| 吉牟田 淳嗣 | 24 |
| 竹内 刀介 | 20 |
| 井上 幸涼 | 14 |
| 岡本 和樹 | 7 |
| 小菅 遥平 | 3 |
| 重松 篤弘 | 1 |

井上の案件は、案件テーブルに **1件（ベネリック 12万円）しかない**。
にもかかわらず日次投稿の受注見込みは 9/10 夕で 25,198,460円。この2つは別の場所から来ている。

**原因**（2026-09-12 追記・特定済み）

読んでいるレポートが**そもそもパイプラインのレポートではない**。

取り込み元は `MSE_26MM計上予定`（検収日基準）／`MSE_26MM受注予定実績`（受注日基準）系、
つまり **計上ステータス軸のレポート**。`analyze-pipeline-mse` のリファレンスにも
「Salesforce案件レポート（計上予定）は基本的に確度の高い案件群」「確度A/B/C/Dは
rep_MSE側のパイプライン行で見る」と明記されている。

データがそれを裏づけている。案件テーブルの確度（`prob`）の出現は:

| 確度 | 件数 |
|---|---:|
| 受注 | 40 |
| （空＝ロスト・ペンディング） | 19 |
| B | 4 |
| D | 2 |
| **A / C / C+** | **0** |

`check-sf-sheet-consistency` が対象にしている確度は「実績／A／B／C／C+／D」。
そのうち **A・C・C+ が1件も入っていない**。

進捗別に金額を見ると、中身の偏りがはっきり出る:

| 進捗 | 件数 | 金額 |
|---|---:|---:|
| ロスト・ペンディング | 19 | 21,186,200円 |
| 入金済 | 34 | 4,140,000円 |
| 提案中（B） | 4 | 3,330,000円 |
| 受注 | 3 | 2,121,600円 |
| リード（D） | 2 | 700,000円 |
| 請求書依頼済 | 1 | 550,000円 |
| 検収済 | 2 | 240,000円 |

**生きている見込み案件（B・D）は6件・4,030,000円しかなく、金額の66%はロスト・ペンディング。**
確定済み（受注以上）を足しても7,051,600円。
これでは、広瀬さん15,000,000円・植松さん10,000,000円という月間受注目標に対する
「見込み」を積み上げようがない。

つまりフィルタの掛け違いではなく、**参照しているレポートの種類が違う**。
計上予定レポートは「いつ売上が立つか」を見るためのもので、
「いま何を追っているか」を見るためのものではない。

**対処**

1. 取り込み元を、確度A/B/C/C+/Dを持つパイプライン側のレポートに変える
   （`MSE_26通期計上予定` 系ではなく、確度列を持つ案件レポート。
   どのレポートが該当するかはSF側で要確認）
2. あるいは計上予定レポートと併読して、確定分＝計上予定／見込み分＝パイプライン、と
   2系統に分けて取り込む。`ChoreiAgg.gs` の `STAGE_CATEGORY` はこの2系統を
   カテゴリで吸収できる形にしてある
3. どちらにせよ、取り込み時に**確度が空の行の割合**を `importLog` に残すこと。
   いま「A・C・C+が0件」に誰も気づけないのは、取り込みが何も報告していないため

既知のレポートIDは `registry/data-sources.yaml` の `sf_report_keijo` / `sf_report_juchu`
（2026-05〜12の月別）に登録済み。朝礼ボードがどれを読んでいるかは、
本体のソースを見れば確定する。

### 2. 【致命】担当者マスタに無い人の数字は、全部落ちる

`members` シートに登録されているのは11名。ここに **吉牟田・小菅・重松が居ない**。
名前からIDへの名寄せに失敗すると `memberId` / `ownerId` が空のまま保存され、
担当者別の集計からは一切拾われない。

実データでの欠落量:

| シート | 症状 |
|---|---|
| 案件（deals） | `ownerId` が空の行が4行（吉牟田の2案件・**8,780,000円**）。うちJR東海リテイリング・プラスが8,660,000円 |
| 日次履歴（朝礼/終礼の取り込み分） | 164行中 **78行（48%）** が `memberId` 空。吉牟田41行・小菅37行 |
| 月次目標の取り込み分 | 24行中9行が `memberId` 空。吉牟田の2026-07受注目標 20,777,400円 などが宙に浮いている |

`ownerName`（例: `吉牟田 淳嗣`）は入っているので、**名前は取れているのにIDに変換できていない**だけ。

**修正方針**
- `members` シートに吉牟田・小菅・重松を追加する（退職・異動なら `active=FALSE` で登録し、
  過去分の名寄せは効くようにする）
- 名寄せに失敗したら黙って空にせず、`importLog` に警告を1行残す。
  いま気づけないのは、失敗が記録されていないため
- 名寄せは `sfName` の完全一致だけでなく、空白を除去した比較にフォールバックさせる
  （`吉牟田 淳嗣` / `吉牟田　淳嗣` / `吉牟田淳嗣` が混在しうる）

### 3. 【重大】月キーがゼロ埋めされておらず、22セルが別の月に集計される

`juchuMonth` / `kenshuMonth` は本来 `2026-09` 形式だが、**1桁月の行が `2026-9` になっている**。

```
juchuMonth の実在値: 2026-01 … 2026-11, 2026-2, 2026-3, 2026-5, 2027-03, 2027-04
kenshuMonth の実在値: 2026-01 … 2026-12, 2026-2, 2026-3, 2026-5, 2026-9, 2027-03, …
```

`'2026-09'` で突合する集計は、`'2026-9'` の行を **静かに落とす**。
不整合セルは22（案件9件ぶん・受注金額合計 2,140,000円）。

2026年9月の計上見込みで実測すると:

| | 金額 |
|---|---:|
| 現状（`kenshuMonth == '2026-09'`） | 600,000円 |
| 月キー正規化後 | 1,300,000円 |
| **取りこぼし** | **700,000円**（株式会社PFU／検収日 `2026/9/10`） |

元データの日付表記自体も `2026/03/20` と `2026/3/20` が混在している（258セル中18セルがゼロ埋めなし）。
ただし `2026/02/28` → `2026-2` という行もあるので、**月キーは日付セルの表示値ではなく
取り込み時の生文字列から作られており、そこでゼロ埋めしていない**。

**修正方針** — 月キーを文字列操作で作るのをやめ、Dateに正規化してから組み立てる。

```javascript
// NG: 生文字列を '/' で割って繋ぐだけ（'2026/3/20' -> '2026-3'）
// OK:
function toMonthKey_(v) {
  if (!v) return '';
  var d = (v instanceof Date) ? v : new Date(String(v).replace(/-/g, '/'));
  if (isNaN(d.getTime())) return '';
  return Utilities.formatDate(d, 'Asia/Tokyo', 'yyyy-MM');
}
```

既存の22セルも、この関数で洗い替えする移行処理が要る。

### 4. 【重大】案件の一意キーが衝突する（`oppId` が全行空）

案件の主キーは `lineId = 会社名|商品名|金額` で作られている。
そして **`oppId` は129行すべてが空** ＝ SalesforceのIDを取り込んでいない。

その結果、同じ会社・同じ商品・同じ金額の案件が別物として区別できず、実際に衝突している:

```
2件 モンテ物産株式会社|予約販売_更新|60000
2件 株式会社フレーバーライフ社|イーレコ更新|120000
```

更新案件は毎年同じ会社・同じ商品・同じ金額で発生するので、**この衝突は今後必ず増える**。
衝突すると、再取り込みのupsertで片方がもう片方を上書きし、
確度変更履歴やTODOの紐づけが別の案件に付く。

**修正方針** — SalesforceのOpportunity Id（18桁）を取り込んで `oppId` を主キーにする。
`lineId` は表示・過去互換用に残す。移行時は既存の `lineId` → `oppId` の対応表を一度作る必要がある。

### 5. 【重大】目標値のマスタが2つあり、値が食い違っている

同じ2026-09の目標が、2つのシートで違う値を持っている。

| 担当 | `members.targetKeijo` | `monthTargets`（2026-09） | 差 |
|---|---:|---:|---:|
| 広瀬 | 7,400,000 | 13,000,000 | **5,600,000** |
| 植松 | 3,700,000 | 5,800,000 | **2,100,000** |
| 井上 | 5,300,000 | 5,000,000 | 300,000 |

受注目標のほうは3名とも一致している（15,000,000 / 10,000,000 / 3,000,000）ので、
**計上目標だけが片方だけ更新されて放置されている**状態。
どの画面がどちらを読むかで達成率が変わる。

さらに `monthTargets` には2026-09の行が **広瀬・植松・井上の3名分しかない**。
竹内・岡本・伊集院・木戸・瀧山には目標行が無いため、日次投稿の `goal` が0で出ている
（伊集院 9/10 受注見込3,136,000に対し goal 0）。達成率を出すと0除算になる。

**修正方針**
- 目標の正は `monthTargets` 一本にする。`members.targetJuchu/targetKeijo` は

- `goal` は「目標−見込」の自動計算と手入力が混在している
  （広瀬・植松は自動計算に一致、木戸 9/9 は goal 1,975,000 で目標0と整合しない）。
  どちらかに統一する

### 8. 【中】日次の受注見込みは案件テーブルと無関係なスナップショット

`dailyAm` / `dailyPm` の `juchuFc` / `keijoFc` は投稿時点の値がそのまま保存されており、
案件テーブルから再計算できない。実データの動きが不自然:

| 日付 | 担当 | 朝の受注見込 | 夕の受注見込 |
|---|---|---:|---:|
| 2026-09-10 | 井上 | 12,566,730 | **25,198,460** |
| 2026-09-10 | 植松 | 3,041,312 | 3,041,312 |
| 2026-09-09 | 広瀬 | 2,421,205 | 2,520,050 |

井上は1日で受注見込みが倍になっているが、案件テーブルに井上の案件は1件（12万円）しかない。
月間受注目標も3,000,000円。**この数字がどこから来ているのか、データ上たどれない。**

また朝の投稿の `postedAt` に `2:03` `2:52` `3:13` `3:21` `22:10` が混じっており、
「どの日の朝礼か」の日付決定ロジックがタイムゾーン／深夜跨ぎで揺れている可能性がある。

**修正方針**
- `juchuFc` / `keijoFc` は案件テーブルから導出し、スナップショットは
  「そのとき何が見えていたか」の監査用に別列で保持する
- 導出できない手入力値を残すなら、画面上で「手入力」と明示する
- 日付決定は `Utilities.formatDate(new Date(), 'Asia/Tokyo', 'yyyy-MM-dd')` に統一し、
  ブラウザ側の `new Date()` からは作らない

## UI側の指摘（ソース未確認・仮説）

データからは断定できないため、コードを見て確認すること。

### A. 「指示を出す」で完了にした指示が、また表示される

`orders` シートの13件を見ると、**`doneAt` が入っている9件も全て `active=TRUE` のまま**。
つまり完了操作は `doneAt` / `doneBy` を書くだけで、`active` は落としていない。

疑わしい順:

1. **一覧の抽出条件が `active` だけを見ている** — 完了しても `active=TRUE` なので再表示される。
   抽出条件を `active === true && !doneAt` にする（または完了時に `active=FALSE` にする）
2. **行の特定方法** — `id`（`d67cb5bb` 等）ではなく行番号で書き戻していると、
   並び替えや行挿入が入った瞬間に別の行へ書き込み、対象は未完了のまま残る。
   必ず `id` で検索してから書く
3. **`scope=all` の指示の完了が1つしかない** — `doneAt`/`doneBy` は1組だけなので、
   全体指示は「誰か1人が完了＝全員完了」になる。
   個人ごとに完了させたいなら完了レコードを別シートに分ける必要がある
4. **`due` の形式が混在** — `2026-09-11 18:12` と `9/7/2026` の2種類が入っている。
   期日で表示可否を判定していると、後者のパース結果次第で表示が揺れる
5. **書き込み完了前に一覧を再取得している** — `google.script.run` のコールバックを待たずに
   リロードすると、完了前のデータを読み直して復活して見える

### B. 何かをクリックすると画面が一番上にスクロールする

GASのWebアプリで典型的な原因は3つ:

1. `<button>` に `type="button"` が無い — `<form>` の中だと既定が `type="submit"` で、
   送信→再読込が走って先頭に戻る。全ボタンに `type="button"` を付ける
2. `<a href="#">` をボタン代わりに使っている — `#` への遷移で先頭にジャンプする。
   `href` を消して `<button>` にするか、ハンドラで `event.preventDefault()` を呼ぶ
3. **一覧を `innerHTML` で丸ごと作り直している** — DOMが差し替わるとスクロール位置が失われる。
   更新前後で位置を保存・復元する:

```javascript
var sc = document.querySelector('#list');
var top = sc.scrollTop;
sc.innerHTML = render(items);
sc.scrollTop = top;          // 差し替え直後に戻す
```

行単位の更新なら、そもそも全体を作り直さず該当行だけ差し替えるのが確実。

**GASのソースが無いと4番以降は当てられない。** 朝礼ボードのスクリプトは
スプレッドシートのコンテナバインド型なので、`registry/apps.yaml` にもIDが載っていない。

ローカルPCで以下を実行して、ソースをこのリポジトリに入れてほしい（5分）。

```bash
# 1. スクリプトIDを調べる
#    MSE朝礼ボード_データ を開く
#    → 拡張機能 > Apps Script > 左下の歯車（プロジェクトの設定）
#    → 「スクリプト ID」をコピー

# 2. 取り込む
cd msesalesinoue
git checkout claude/tender-ramanujan-4mmpq0
mkdir -p apps
clasp clone <スクリプトID> --rootDir ./apps/chorei-board

# 3. 認証情報が混じっていないか確認してからコミット
grep -rniE "(password|secret|api[_-]?key|token|Bearer )" apps/chorei-board
git add apps/chorei-board && git commit -m "朝礼ボードのGASソースを取り込み" && git push
```

clasp の初回セットアップは [`gas-backup-runbook.md`](gas-backup-runbook.md) を参照。

ソースが入ったら、上の表の3〜8をパッチとして当てる。
