# MSE朝礼ボード 集計不具合の調査（2026-09-13・全データ版）

> **この文書は [`chorei-board-audit-2026-09-11.md`](chorei-board-audit-2026-09-11.md) を置き換える。**
> 9/11版は `read_file_content` が返したデータに基づいていたが、
> **これは各シートの先頭だけを切り出した抜粋だった**（案件シートは4,720行中129行のみ）。
> 抜粋を全件と誤認したため、9/11版には事実と異なる結論が複数含まれている。
> 何が誤りだったかは [末尾の訂正一覧](#911版の訂正一覧) に全部載せた。
>
> 今回は xlsx でエクスポートし、**全22シート・全行・セル書式まで**読んで検証した。

## 調査方法

`MSE朝礼ボード_データ` を xlsx としてダウンロードし、openpyxl で全件解析した。
セルの型と表示書式も見ているので、「文字列に見えるが実体は日付」のような問題も拾えている。

| シート | 行数 | | シート | 行数 |
|---|---:|---|---|---:|
| 取込_案件 | 4,720 | | 朝礼ログ | 29 |
| 取込_TODO | 2,042 | | 終礼ログ | 28 |
| 監査ログ | 1,396 | | 指示 | 12 |
| 行動履歴 | 582 | | 指示回答 | 31 |
| TODOログ | 132 | | メンバー | 11 |
| 月次 | 75 | | 月別目標 | 3 |

**数式は1セルも無い。** 22シートすべてが値のみ。集計はすべてGAS側で行われている。

## 結論

数字が合わない直接の原因は、**同じレポートを1日に2回取り込んで倍になっていたこと**。
違和感を覚えた時期（9/10〜9/12）と、二重取り込みが起きていた期間が完全に一致する。

## 1. 【致命】3日間、案件が二重に取り込まれていた

監査ログの `ingest` 行に、取り込んだファイル数と件数が記録されている。

```
2026-09-08 18:02:50  files=1  deals=1636  todos=730
2026-09-08 18:02:50  files=1  deals=4560  todos=1989   ← レポートの範囲が広がった
2026-09-09 07:30:36  files=1  deals=4572  todos=1993
2026-09-10 07:30:43  files=2  deals=9172  todos=3989   ★ 約2倍
2026-09-11 07:31:16  files=2  deals=9330  todos=4056   ★ 約2倍
2026-09-12 07:30:36  files=2  deals=9422  todos=4075   ★ 約2倍
2026-09-13 07:30:34  files=1  deals=4720  todos=2042   ← 1通に戻って半分
```

**`files=2` の日は案件数がちょうど倍になっている。**
9/13 に1通に戻ったら 4,720件。実態は約4,700件で、9/10〜9/12 の 9,300件は水増し。

つまりあの3日間、朝礼ボードに出ていた個人別の受注見込み・計上見込みは
**全員ぶん、ほぼ2倍で表示されていた**。

### なぜ二重になるか

取り込みはメール添付のCSVを読む方式（`ingest | no new mail` というログがある）。
8/31 のエラーログにファイル名が残っている:

```
列が一致しません [GAS朝礼用MSE　全案件2026年受注-2026-08-31-05-00-13.csv]
```

同じレポートが1日に2通届くと、2通とも処理して**追記**してしまう。
重複排除が効かないのは、一意キーが弱いから（→ [不具合3](#3-致命-案件の一意キーが衝突している-oppidが全行空)）。

### 対処

1. 取り込みの入口で、**その回に処理する全ファイルをマージしてから**書き込む。
   1ファイルずつ順に追記しない
2. 書き込み前に `lineId + side` で重複を落とす。
   より確実には、書き込みを全消し→全書き込み（truncate & load）にする
3. `ingest` のログに「重複で落とした件数」を必ず残す。
   いま3日間気づけなかったのは、ログが `files=2` としか言わないため
4. 当面の運用回避策：`files=2` のログが出た日は、その日の数字を信用しない

## 2. 【致命】月キーの列が日付セルになっている

`juchuMonth` / `kenshuMonth` は `2026-09` という文字列のはずだが、
**実体は日付セル**（`2026-09-01 00:00:00`）だった。4,720行すべて。

GASが `'2026-09'` という文字列を書き込むと、Googleスプレッドシートが
**勝手に日付として解釈してしまう**。列がプレーンテキスト書式になっていないため。

| 列 | セルの型 | 表示書式 |
|---|---|---|
| `juchuMonth` | datetime（4,720行すべて） | `yyyy-mm` 89% / `yyyy-m` 11% |
| `kenshuMonth` | datetime（同上） | `yyyy-mm` 88% / `yyyy-m` 12% |

### なにが起きるか

GASが `getValues()` で読み戻すと **Dateオブジェクト**が返る。
したがって

```javascript
if (row[COL.juchuMonth] === '2026-09')          // 常に false
if (String(row[COL.juchuMonth]) === month)      // "Tue Sep 01 2026 00:00:00 GMT+0900..." なので false
```

**月で絞る集計は、条件に一致する行が1件も無い**状態になりうる。

### 対処

月キーを列に持たせるのをやめ、`juchuDate` から読むたびに導出するのが一番確実。
列を残すなら、書き込み前に必ずテキスト書式にする。

```javascript
sheet.getRange(2, colMonth, sheet.getLastRow() - 1, 1).setNumberFormat('@');
```

読む側は、Dateでも文字列でも同じ結果になる関数を通す
（`apps/chorei-board-fix/ChoreiFix.gs` の `toMonthKey_()` がこれ）。

## 3. 【致命】 案件の一意キーが衝突している（`oppId`が全行空）

`oppId` は **4,720行すべて空**。主キーは `lineId = 会社名|商品名|金額` で作られている。

更新・定期系の案件は毎年おなじ会社・おなじ商品・おなじ金額で発生するので、必ず衝突する。
実データで **172キー・495行**が衝突し、**うち169キーは中身の違う別案件**だった。

```
■ ペルシア株式会社|イプシロン定期_更新|60000
    260226_イプシロン定期(更新)   2026-02-18  入金済      伊集院
    270226_イプシロン定期(更新)   2027-02-25  提案中（B）  伊集院

■ 株式会社ネットプライス|イーレコ更新|120000
    260201_イーレコ(更新)        2026-01-09  ロスト・ペンディング  伊集院
    260501_イーレコ更新          2026-04-27  入金済             伊集院
    270501_イーレコ更新          2027-04-02  内示（A）          伊集院

■ 株式会社三保製薬研究所|定期購入|300000
    20250212　PG定期                    2026-01-13  入金済   竹内
    20260826【WEB】三保製薬研究_定期購入   2026-08-31  検収済   木戸    ← 担当者すら違う
```

再取り込みのupsertで片方がもう片方を上書きし、確度変更履歴やTODOの紐づけが
**別の案件に付く**。三保製薬のように担当者が違うケースでは、他人の数字に混ざる。

**対処** — SalesforceのOpportunity Id（18桁）を取り込んで主キーにする。
これは [不具合1](#1-致命3日間案件が二重に取り込まれていた) の重複排除の前提でもある。

## 5. 【重大】目標マスタが二重化している

`月別目標` は 2026-09 の3名分（広瀬・植松・井上）しか無い。
一方 `メンバー` シートにも `targetJuchu` / `targetKeijo` 列があり、値が食い違う。

| 担当 | メンバー.targetKeijo | 月別目標.targetKeijo | 差 |
|---|---:|---:|---:|
| 広瀬 | 7,400,000 | 13,000,000 | 5,600,000 |
| 植松 | 3,700,000 | 5,800,000 | 2,100,000 |
| 井上 | 5,300,000 | 5,000,000 | 300,000 |

**対処** — 正は `月別目標` 一本にする。月初に `active` 全員分の行を自動生成する。

## 7. 【中】指示の完了が効いていない

`指示` シート12件は **全件 `active=TRUE`**。うち10件は `doneAt` が入っている。
完了操作は `doneAt` / `doneBy` を書くだけで、`active` は落としていない。

完了時刻に症状そのものが残っている:

```
2026-09-10 9:05:05  SomriXさんの件の進捗を報告する
2026-09-10 9:05:10  jointプッシュ3社 西原商会、カトージ、日本ハム
2026-09-10 9:05:21  JointAIFlowのリスト準備
2026-09-10 9:05:24  帳票系オプションの更新一覧の状況報告
2026-09-10 9:05:32  パートナー施策、新たに当たる5社をピックアップ
2026-09-10 9:05:42  代理店施策3社にプッシュ連絡
```

**37秒で6件**、別々の日に出した指示がまとめて完了にされている（9/9 にも14秒で2件）。
一度完了にしたものが溜まって再表示され、まとめて消し直した動きに見える。

`doneBy` は10件すべて「井上」。指示を受けた本人ではなく出した側が消しているので、
担当者の画面では消えていない可能性もある。

疑わしい順（コードを見ないと確定できない）:

1. **一覧の抽出条件が `active` だけを見ている** → 抽出を `active && !doneAt` にする
2. **行の特定が `id` ではなく行番号** → 並び替えや行挿入で別の行に書き込む
3. **完了状態が1組しかない** — `scope=all` の指示（2件）は
   「誰か1人が完了＝全員完了」にしかできず、個人ごとの完了を記録する場所がない
4. **書き込み完了前に一覧を再取得している** — `google.script.run` のコールバックを待っていない

## 8. 【中】クリックすると画面が先頭にスクロールする

データからは判断できない。GASのWebアプリで典型的なのは3つ。

1. `<button>` に `type="button"` が無い — `<form>` 内だと既定が submit で、送信→再読込が走る
2. `<a href="#">` をボタン代わりに使っている — `#` への遷移で先頭にジャンプする
3. **一覧を `innerHTML` で丸ごと作り直している** — DOMが差し替わると位置が失われる

```javascript
var sc = document.querySelector('#list');
var top = sc.scrollTop;
sc.innerHTML = render(items);
sc.scrollTop = top;
```

行単位の更新なら、そもそも全体を作り直さず該当行だけ差し替えるのが確実。
