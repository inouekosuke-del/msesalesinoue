# 朝礼ボード「朝礼・終礼のまとめ」が重い ｜ 2026-09-15

**症状** — まとめビュー（朝礼／MSE／2026-09-15）が「読み込み中...」のまま長時間出ない。

## 効いている数字

| | 値 | 出どころ |
|---|---|---|
| まとめに**表示したい**行数 | **7行**（当日の朝礼提出） | 朝礼シート |
| 裏で抱えている案件明細 | **4,720行** | 設定シート `lastIngestCount = 4720/2042` |
| 同 TODO | **2,042行** | 同上 |
| シート数 / ファイルサイズ | 23シート / 410KB | MSE朝礼ボード_データ |

**7行を出すために数千行を舐めている**構図。まとめビューはヘッダに
「Slackに流れるのと同じ内容です」とある通りSlack投稿と同じペイロードを組むため、
各案件の商談名・受注日を `dealId` で案件明細から引き、さらに上長指示・TODO・
（Slack投稿に「今日の予定」がある以上）カレンダーまで取りに行っている可能性が高い。

## 疑う順番（Apps Scriptエディタで確認）

1. **案件明細の全件読み込みがループの中にある**
   `getDataRange().getValues()` が案件ごと・メンバーごとに呼ばれていないか。
   4,720行×19列 ≒ 9万セルの読み込みが90案件分走れば、それだけで分単位になる
2. **CalendarApp をメンバー数ぶん叩いている**
   1回0.5〜2秒。7名で数秒〜十数秒。まとめビューに予定が要るのかを含めて見直す
3. **google.script.run が1本の同期呼び出しで、全部揃うまで何も描画しない**
   「読み込み中...」のまま固まるのはこの形。失敗時も無言で止まる

## 直し方（効果の大きい順）

1. **提出時にレンダリング済みブロックを保存する（本命）**
   Slack投稿用の本文は提出時点で組み立てている。同じ文字列を朝礼シートの
   `rendered` 列に入れておけば、まとめビューは**当日7行を読んで連結するだけ**になり、
   案件明細を触る必要が消える。Slack投稿が落ちている件の再投稿にも同じ列が使える
2. **索引を1回だけ作る**
   案件明細は `getValues()` 1回 → `lineId` をキーにした Map を作ってから O(1) で引く。
   ループ内で `find()` / `getDataRange()` を呼ばない
3. **CacheService でまとめ結果をキャッシュ**
   キー `summary_<kind>_<team>_<date>`、TTL 5〜10分。内容が変わるのは誰かが提出した時だけなので、
   提出時にそのキーを捨てれば整合も取れる
4. **読む範囲を絞る**
   `getDataRange()` ではなく `getRange(1, 1, lastRow, 必要列数)`。当日分だけなら日付で先に絞る
5. **段階描画**
   メンバー単位で返して、届いた順に描く。全件揃うまで真っ白にしない。
   `withFailureHandler` を必ず付ける（今は失敗しても「読み込み中...」のままに見える）

## 現状ここで止まっている理由

このリポジトリからは **GASのソースもトリガーも取得できない**（Drive APIはApps Scriptを返さない。
`MSE朝礼ボード_ソース` フォルダは空）。上記1〜5はどれもコードを見ないと確定できない。

**最短の解除方法**：Apps Scriptエディタでまとめビューのバックエンド関数
（`doGet` から呼ばれる集計関数と、それが呼ぶシート読み込み関数）と `Index.html` の
`google.script.run` 周りを貼れば、そのままパッチを書ける。
恒久的には `docs/gas-backup-runbook.md` をローカル実行してソースをGit管理下に置く。
