# Salesforceレポート項目仕様（日次差分・活動量可視化用）

作成日: 2026-09-14
関連: [`sf-daily-diff-design.md`](sf-daily-diff-design.md)

日次差分と活動量可視化のために新規作成するSalesforceレポートの項目定義。
既存の「GAS朝礼用MSE　全案件2026年受注」が抱える問題（キーに金額が含まれる／
活動日の列がない／履歴が残らない）を、レポート設計の時点で解消することを目的とする。

## 構成：2本立て

| | 単位 | 用途 | 想定行数 |
|---|---|---|---|
| レポートA `MSE_日次_商談_v1` | 1商談1行 | 日次差分・停滞検知・活動量 | 数百 |
| レポートB `MSE_日次_商談商品_v1` | 1商談商品1行 | 金額内訳・商品分析 | 2,000+ |

既存の「朝礼用」は商談商品レベルで2,390行あり、差分と活動量の用途には粒度が細かすぎる。
Aを主軸とし、Bは既存の「朝礼用」「商品分析」の統合先として後続で整備する。

**レポートAは1商談1行とする。** 既存パイプラインは同一案件を「受注」「計上」の2行に
複製している（lineId末尾 `#K`）が、受注日と検収日を同一行に列として持てば複製は不要。
行数が半減し、差分処理も単純になる。

## レポートタイプの選択

### レポートA：標準レポートタイプ「商談」

**「商談と商品」を選ばないこと。** 既存の「GAS朝礼用MSE　全案件2026年受注」がこれに該当し、
商品を持つ商談が商品数だけ行に展開されるため1商談1行にならない（現行2,390行の要因）。

「商談」タイプで以下が取得できる：

- 商談ID（18桁で出力）
- 取引先ID / 取引先名（「取引先」セクション。結合不要）
- 最終活動日（標準項目）
- ステージ最終変更日（標準項目。項目検索で存在を確認すること。無ければ「商談履歴」で代替）
- 受注予定日・検収予定日等のカスタム項目（商談オブジェクトのものは全て選択可）

**形式は表形式（Tabular）。** サマリー形式・マトリックス形式・結合レポートは使用不可。

### レポートB：既存レポートの複製を推奨

既存レポートの検索条件に「すべての商談商品名」とあることから、カスタムレポートタイプが
使われていると見られる。ゼロから作り直すより「名前を付けて保存」で複製し、列を追加する方が安全。

新規作成する場合、標準の「商談と商品」は**商品が登録されていない商談を除外する**点に注意。
商品なしの商談も対象にするなら「商談（商品ありまたはなし）」系、または既存のカスタムタイプを使う。

### 将来の拡張で使うレポートタイプ

| 用途 | レポートタイプ |
|---|---|
| ステージごとの滞留日数・確度の遷移 | 商談履歴（ステージ変更履歴のスナップショット） |
| 項目単位の変更履歴（金額の変更時期など） | 商談項目履歴 |
| 商談に紐づく活動の件数・内容 | 商談とToDo、行動 |

後者2つは1商談が複数行に展開されるため、**レポートAには混ぜない**（差分のキーが壊れる）。
活動量はToDoリストビュー（`filterName=MSE`、`alert-overdue-mse` が使用）と商談IDで突き合わせる。
「商談履歴」はステージ最終変更日が標準項目にない場合の代替にもなるが、別レポートとして持つこと。

## レポートA 項目一覧

### ① キー（差分の成立条件）

| 項目 | 優先度 | 用途 |
|---|---|---|
| 商談ID（18桁） | **必須** | 差分の主キー。現行 lineId は「社名\|商品名\|金額」構成のため金額変更で別レコード扱いになる |
| 商談名 | 必須 | 表示用 |
| 取引先ID（18桁） | **必須** | 社名変更・表記ゆれ・同名企業の衝突に対する耐性 |
| 取引先名 | 必須 | 表示用 |
| レコードタイプ | 必須 | MSE / その他の切り分け |

### ② 活動量

| 項目 | 優先度 | 用途 |
|---|---|---|
| 最終活動日（LastActivityDate） | **必須** | 実際の顧客接触の有無。現行レポートに存在しない |
| 最終更新日（LastModifiedDate） | 必須 | レコード更新日。活動量の代用にはならないが完全放置の検出に使う |
| ステージ最終変更日 | 推奨 | 「更新はされているがステージは動いていない」の検出 |
| 作成日 | 必須 | 滞留日数の起点 |
| 次回ToDo期日 / 未完了ToDo件数 | — | 商談レポートには乗らない見込み（後述） |

停滞判定は 最終活動日 / ステージ最終変更日 / 最終更新日 の3段階で見る。
「更新はされているが顧客接触がない」状態が最も見落とされやすい。

### ③ 日付

受注予定日、検収予定日、完了予定日（CloseDate）、契約開始日、契約終了日、
受注日（実績）、失注・ペンディング日

### ④ 金額

金額（売上）、原価、粗利、期待収益、システム利用料

`check-report-mse` のKGIが「計上売上／計上粗利／受注売上／システム利用料」の4指標のため、
これらが直接取得できる形にしておくと週次レポートと接続できる。

### ⑤ ステータス

進捗状況（ステージ）、確度%、確度ランク（実績/A/B/C/C+/D）、失注理由

確度ランクは `check-sf-sheet-consistency` 系3スキルが個人チェックシートと突合している
区分そのもの。文字列で持たせると突合処理が簡潔になる。

### ⑥ 担当

所有者名、所有者ID（またはユーザ名）、所有者部署

既存の `ownerId` は `ijuin` のような短縮形。`alert-overdue-mse` が保持するSlackメンバーIDと
紐付けるキーになるため、表記を固定すること。

## 拡張用項目

レポート項目は後から追加できるが**過去に遡れない**。
今の時点で入れておけば翌日から履歴が蓄積される。

| 項目 | 後から何ができるか |
|---|---|
| リードソース（流入元） | 流入元別の歩留まり・ROI |
| キャンペーン | 施策の効果測定 |
| 新規 / 既存 区分 | 新規開拓と既存深耕の比率 |
| 商品カテゴリ（大） | カテゴリ別の伸び |
| 競合 | 失注分析 |
| 更新元商談 | 更新案件の継続率 |
| 契約期間（月数）／課金区分（月額・一時金） | MRR・LTVの算出 |
| 初回商談日 | リード→商談→受注のリードタイム |

## レポートB 項目一覧

レポートAのキー（商談ID・取引先ID・所有者）に加えて：

商談商品ID（18桁）、商品名、商品コード、数量、単価、売上、原価、粗利、
納品日、外注先、外注先納品日、商品カテゴリ（大）、商品カテゴリ（中）

## 設計ルール

守らないと差分が壊れる。

1. **フィルタに相対日付を使わない**
   「過去30日」のような条件は対象範囲が毎日ずれる。昨日対象だった案件が今日は範囲外という
   だけで「消えた」と誤検知する。「常時」または固定年度で指定する。
2. **並び替えは商談ID昇順で固定**
   並び順が変動すると差分処理が不安定になる。
3. **集計・グルーピングを付けない**
   明細行のみ。マトリックス形式は使用不可（`alert-overdue-mse` にも同旨の注記あり）。
4. **列の追加は右端のみ**
   既存GASが列位置で読んでいる可能性が高く、途中挿入はエラーを出さずに壊れる。
   ヘッダー名で読む実装に改修するまでは、追加は必ず右端。
5. **レポート名にバージョンを付ける**
   列構成を変更する際はv2を新規作成して並走させ、切替完了後にv1を停止する。
   稼働中のパイプラインを止めずに変更できる。

## 未確認事項

### 行数上限に達している可能性

現行の「GAS朝礼用MSE　全案件2026年受注」は合計レコード数2,390。
Salesforceのレポート表示上限は2,000行のため、**メールに載る行が2,000行で頭打ちになり、
毎日約390行が取り込まれていない可能性がある。**

確認方法：`取込_案件` タブの行数が 2,000（受注/計上の2系統で4,000）ちょうどで
頭打ちになっていないか確認する。該当する場合は取りこぼしが発生している。

レポートAを商談レベルにすると行数が数百まで減るため、この問題も同時に解消される。

### ToDoは同一レポートに含められない

「次回ToDo期日」「未完了ToDo件数」はToDo（Task）オブジェクト側の情報のため、
商談レポートに明細として出せない。`alert-overdue-mse` が既にToDoリストビュー
（`filterName=MSE`）で取得しているため、**活動量はそちらと商談IDで突き合わせる。**
レポートAに商談IDがあれば接続できる。
