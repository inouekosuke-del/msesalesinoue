## 3. 最大の問題：スキルがデータを「名前」で参照している

AIオフィスとして致命的なのはここ。スキルの多くが参照先を **ファイル名の文字列** で書いており、
安定した Drive ID を持っていない。

| スキル | 参照先の書き方 | リスク |
|---|---|---|
| `analyze-pipeline-mse` | ID あり（2件） | 低 |
| `check-report-mse` | ID あり（1件） | 低 |
| `check-sf-sheet-consistency`（3種） | ID あり（5名分） | 低。ただし **3スキルに同じ表をコピー** |
| `track-d-case-mse` | 「【全体】チェックシート2026 MSE」名前のみ | **高** |
| `mse-weekly-kpi-recovery` | 「mse_業績管理_2026」「mse_商談分析_2026」名前のみ | **高** |
| `mse-shodan-gas` | 同上、名前のみ | **高** |
| `alert-overdue-mse` | 「MSE_26MM計上予定」等 SFレポート名のみ | **高** |

誰かがシート名を変えた瞬間、スキルは**エラーも出さずに別ファイルを掴むか、静かに失敗する**。
さらに `check-sf-sheet-consistency` 系はデータソース表を3スキルに複製しているため、
1人分のシートを差し替えたら3箇所を直す必要があり、直し忘れれば結果が食い違う。

## 4. 参照先データの鮮度

台帳がないため誰も気づいていないが、棚卸しで判明した点：

- `【井上】個人チェックシート2026` の最終更新は **2026-06-09**（3ヶ月前）。
  これを読む `check-sf-sheet-consistency` 系3スキルは、古いデータを正として突合している可能性がある。

台帳に「最終更新日」を持たせれば、こういう死んだデータソースは自動で検出できる。

## 5. 依存関係が誰にも見えない

`mse_業績管理_2026` と `mse_商談分析_2026` は **田村さん所有**、
`ms事業部_アクションプラン` は **末次さん所有**、
`業績レポート` `【全体】チェックシート2026 MSE` は共有ドライブ。

つまり自分のスキルが「他人が自由に触れるファイル」に依存している。
所有者側は、そのファイルがAIワークフローの入力になっていることを知らない。
`registry/data-sources.yaml` はこの依存を明示するためのもの。
