## 3. スキルのデータ参照方式（再検査済み）

**訂正**：初回検査はURL形式（`spreadsheets/d/<ID>`）しか見ておらず、`fileId: \`<ID>\`` のように
裸で書かれたIDを取りこぼしていた。裸ID・SalesforceレポートIDを含めて再検査した結果が以下。

| スキル | 参照方式 | 評価 |
|---|---|---|
| `alert-overdue-mse` | SFレポートIDを**月別に8ヶ月分**、SlackチャンネルID、メンバー→SlackメンバーIDまで表で保持 | **最も整備されている。他スキルの手本** |
| `analyze-pipeline-mse` | Drive ID 2件 | 良好 |
| `track-d-case-mse` | Drive ID 1件（`fileId:` 形式） | 良好 |
| `check-report-mse` | Drive ID 1件 | 良好 |
| `check-sf-sheet-consistency`（3種） | Drive ID 5名分 | ID自体は良好。ただし**同じ表を3スキルに複製** |
| `mse-shodan-gas` | Drive ID 2件（スプレッドシート＋GASスクリプト） | 良好 |
| `mse-weekly-kpi-recovery` | Drive ID 3件。ただし**業績レポート（rep_MSEタブ）のIDだけ無い** | 軽微な欠落 |

つまり「スキルが名前でデータを探していて危険」という当初の見立ては**誤り**だった。
ID参照は概ねできている。残る実際のギャップは次の3点のみ：

1. `mse-weekly-kpi-recovery` が読む「業績レポート」のスプレッドシートIDが未記載
   （ユーザーがURLを渡す運用でカバーされているが、台帳に載せるべき）
2. `alert-overdue-mse` の **2027-01〜04（同FY26）のSFレポートIDが未提供**
   ※スキル本文にも「対象になったらユーザーに依頼する」と明記済み。期限は2026年内
3. `check-sf-sheet-consistency` 系3スキルのデータソース表が3重複

**本当の問題は参照方式ではなく、この情報がスキルの中に閉じていて横断で見えないこと。**
`alert-overdue-mse` が持つSFレポートID表は他スキルからは存在すら分からない。
台帳（`registry/`）はそれを外に出すためのもの。

台帳がないため誰も気づいていないが、棚卸しで判明した点：

`mse_業績管理_2026` と `mse_商談分析_2026` は **田村さん所有**、
`ms事業部_アクションプラン` は **末次さん所有**、
